# 测试上传图片功能一直在上传中，订单也无法提交

## 产品经理

根据当前问题和项目架构，需要优先修复核心功能并完善后续流程。

### 功能列表

1.  **图片上传修复**
    *   前端：优化上传组件，增加明确的状态反馈（上传中、成功、失败）、错误提示和重试机制。
    *   后端：检查并确保图片上传至 Supabase Storage 的 API 接口可用，返回正确的公开 URL。
    *   存储：确认 Supabase Storage 中对应 Bucket 的权限策略允许认证用户上传。

2.  **订单提交修复**
    *   前端：确保订单表单数据（含图片URL）收集完整，提交前进行必填项校验。
    *   后端：确保 `/api/orders` 创建接口存在且逻辑正确，能处理关联的订单项和图片URL。
    *   数据库：确保 `orders` 表及相关表（如 `order_items`）的插入操作符合 Schema 约束。

3.  **订单状态流转与任务生成**
    *   逻辑：订单创建后，状态应为 `pending_dispatch`。根据业务规则，自动或手动为订单生成初始任务（如编程、加工）。
    *   界面：在订单详情页，允许有权限的用户（如 `office`）推进订单状态，并查看/管理关联任务。

4.  **任务看板与处理**
    *   界面：为 `cnc_program`, `cnc_machine` 等部门角色提供任务列表视图，按状态和优先级筛选。
    *   操作：允许任务负责人更新任务状态（`in_progress`, `completed`），完成任务后自动或提示更新订单状态。

### 验收标准

1.  **图片上传**
    *   用户选择图片后，界面立即显示上传进度条或加载状态。
    *   上传成功后，图片预览正常显示，且能获取到可访问的图片URL。
    *   上传失败时，显示明确的错误信息（如“网络错误”、“文件过大”），并提供“重试”按钮。
    *   单张图片上传时间在合理范围内（如10秒内，视网络环境）。

2.  **订单创建与提交**
    *   在订单创建页，填写所有必填信息并成功上传至少一张图片后，点击“提交”按钮。
    *   系统无报错，按钮状态由“提交中”变为“已提交”。
    *   页面自动跳转至新创建的订单详情页，或订单列表页显示新订单。
    *   在订单详情页能查看到完整的订单信息、客户信息和上传的图片。

3.  **订单与任务流转**
    *   在订单详情页，`office` 或 `admin` 角色能看到“开始处理”按钮，点击后订单状态从 `pending_dispatch` 变为 `programming`，并自动创建第一个“编程任务”。
    *   `cnc_program` 角色在任务列表中能查看到该任务，并将其标记为 `in_progress` 或 `completed`。任务完成后，相关状态在订单详情页同步更新。

4.  **核心流程闭环**
    *   一个测试订单能完整走通“创建 -> 任务分配 -> 任务处理 -> 状态推进 -> 交付”的流程。
    *   每个关键状态变更，相关角色都能在界面中看到更新，并收到必要提示。

-- =============================================
-- 创建函数：生成订单号
-- =============================================
create or replace function generate_order_number(prefix text default 'ORD')
returns text as $$
declare
  next_val integer;
begin
  -- 获取当前日期的下一个序号（每天重置）
  select coalesce(max(
    case 
      when order_number like prefix || '-' || to_char(now(), 'YYYYMMDD') || '-%' 
      then substring(order_number from length(prefix || '-' || to_char(now(), 'YYYYMMDD') || '-') + 1)::integer
      else 0
    end
  ), 0) + 1 into next_val
  from orders
  where order_number like prefix || '-' || to_char(now(), 'YYYYMMDD') || '-%';
  
  return prefix || '-' || to_char(now(), 'YYYYMMDD') || '-' || lpad(next_val::text, 4, '0');
end;
$$ language plpgsql security definer;

-- =============================================
-- 创建触发器：更新订单更新时间
-- =============================================
create or replace function update_order_timestamp()
returns trigger as $$
begin
  new.updated_at = now();
  return new;
end;
$$ language plpgsql;

create trigger update_orders_timestamp
before update on orders
for each row
execute function update_order_timestamp();

-- =============================================
-- 创建触发器：订单状态变更时记录日志
-- =============================================
create or replace function log_order_status_change()
returns trigger as $$
begin
  if old.status is distinct from new.status then
    insert into operation_logs (user_id, order_id, action, details)
    values (
      auth.uid(),
      new.id,
      'order_status_changed',
      jsonb_build_object(
        'old_status', old.status,
        'new_status', new.status,
        'timestamp', now()
      )
    );
  end if;
  return new;
end;
$$ language plpgsql;

create trigger log_order_status_change_trigger
after update on orders
for each row

async function getUserFromToken(token: string) {
  const { data: { user }, error } = await supabase.auth.getUser(token)
  if (error || !user) return null
  
  const { data: profile } = await supabase
    .from('profiles')
    .select('*')
    .eq('id', user.id)

// 验证中间件
async function authenticate(req: express.Request, res: express.Response, next: express.NextFunction) {
  const authHeader = req.headers.authorization
  if (!authHeader?.startsWith('Bearer ')) {
    return res.status(401).json({ error: '未授权' })
  }

  const token = authHeader.slice(7)
  const userData = await getUserFromToken(token)
  
  if (!userData) {
    return res.status(401).json({ error: '无效的令牌' })
  }

  ;(req as any).userId = userData.user.id
  ;(req as any).user = userData.user
  ;(req as any).profile = userData.profile
  next()
}

// 管理员权限中间件
async function requireAdmin(req: express.Request, res: express.Response, next: express.NextFunction) {
  const profile = (req as any).profile
  if (!profile || profile.role !== 'admin') {
    return res.status(403).json({ error: '需要管理员权限' })
  }
  next()
}

## 🔍 Bug 风险
1. **订单状态不一致**：数据库 `orders` 表的 `status` 检查约束包含 `rough_machining` 和 `fine_machining`，但前端 `OrderStatus` 类型未包含这些值（仅包含 `'pending_dispatch' | 'programming' | 'pending_delivery' | 'delivered'`）。会导致前端显示和后端验证不匹配。
2. **缺失的表定义**：代码中引用了 `order_items` 表，但在提供的 `schema.sql` 片段中未定义。需要确保完整执行提供的完整版 SQL。
3. **API 端点不完整**：`server/src/index.ts` 中的客户列表 API 在响应前被截断（`return res.status(400).json({`），需补全。
4. **`tracker_code` 验证缺失**：后端创建用户时未验证 `tracker_code` 值是否在 `['A', 'B', 'C']` 范围内。

## 🔒 安全问题
1. **文件上传类型未限制**：`/api/upload` 接口仅限制文件大小，未验证文件类型（如图片扩展名、MIME类型），可能被上传恶意文件。
2. **客户列表权限过宽**：`GET /api/customers` 对所有认证用户开放，但按业务逻辑可能应仅限 `admin` 和 `office` 角色。
3. **SQL 函数安全**：`current_user_role()` 和 `generate_order_number()` 使用 `security definer` 是正确的，但需确保函数体内的查询也安全（如 `generate_order_number` 中的字符串拼接无注入风险，因使用参数化值）。
4. **操作日志用户级联**：`operation_logs` 表的 `user_id` 外键未设置 `on delete` 行为，若用户被删除，日志会变成孤儿数据。建议设置为 `set null` 或 `restrict`。

## ⚡ 性能/设计问题
1. **订单号生成并发竞争**：`generate_order_number()` 函数在高并发插入时可能因 `max()` 查询的竞争条件导致重复订单号。建议使用数据库序列或更可靠的生成策略。
2. **重复定义**：`VALID_ROLES` 常量在 `server/src/index.ts` 中重复定义，应提取为公共常量或从数据库类型派生。
3. **前端类型缺失**：前端 `Profile` 类型包含 `email` 字段，但数据库 `profiles` 表无 `email` 列（存在 `auth.users` 中）。前端类型需调整为 `email?: string` 或从关联查询获取。

## ✅ 建议修复
1. **统一状态定义**：同步前端 `OrderStatus` 类型与数据库约束。
2. **补全 API 逻辑**：完成客户列表等被截断的 API 实现。
3. **增强上传安全**：在 `/api/upload` 添加文件类型白名单验证。
4. **完善权限控制**：审查 API 的角色权限，确保符合最小权限原则。
5. **优化订单号生成**：考虑使用数据库序列或 Redis 原子操作生成唯一订单号。

整体架构良好，但需解决上述问题以确保系统稳定性和安全性。
